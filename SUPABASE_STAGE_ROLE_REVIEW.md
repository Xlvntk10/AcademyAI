## Найденная ошибка плана и тестов

В PostgreSQL 16+ роль с CREATEROLE может создать другую роль и получить ADMIN OPTION на неё, но по умолчанию не получает право SET ROLE. Автоматическая выдача SET зависит от `createrole_self_grant`, по умолчанию пустого. BYPASSRLS не заменяет SUPERUSER и не даёт права переключаться на любую роль.

Старый план создаёт `academy_stage_runtime`, затем пытается выполнить `SET LOCAL ROLE academy_stage_runtime`. Он не учитывал отсутствие SET. На локальном PostgreSQL 17 воспроизведены все признаки:

1. Сессионный пользователь без SUPERUSER, но с CREATEROLE, CREATEDB, BYPASSRLS и CREATE для тестовой базы.
2. Создание stage-объектов проходит.
3. Переключение на runtime отклоняется: **SQLSTATE 42501, ROLE_SWITCH_DENIED**.
4. Старый классификатор получает обёртку SQLAlchemy и возвращает **UNKNOWN**.
5. Вся локальная транзакция откатывается, созданных схем/ролей не остаётся.

Источник поведения: [PostgreSQL: createrole_self_grant](https://www.postgresql.org/docs/17/runtime-config-client.html#GUC-CREATEROLE-SELF-GRANT).

Это конкретный воспроизводимый дефект старого плана и убедительный кандидат на причину пользовательского отказа. Однако старый отчёт не сохранил SQLSTATE; значение `createrole_self_grant` и версия настоящего сервера в прежней инспекции тоже не записывались. Поэтому утверждать, что историческая ошибка доказана на 100%, было бы неверно. Дополненная read-only инспекция теперь показывает необходимые признаки.

Обнаружен недостаток прежних локальных тестов: они использовали `SET LOCAL ROLE` для имитации администратора без SUPERUSER, но `session_user` оставался суперпользователем. PostgreSQL проверяет возможность SET ROLE именно относительно `session_user`, поэтому такой тест пропускал ошибку. Теперь тестовые фикстуры используют `SET LOCAL SESSION AUTHORIZATION`; работающий сценарий явно задаёт разрешённое автоматическое SET **только внутри локальной тестовой транзакции**. Отдельный тест с пустым self_grant воспроизводит отказ. [PostgreSQL: SET ROLE](https://www.postgresql.org/docs/17/sql-set-role.html).

## Что исправлено без расширения прав Supabase

- Добавлен `scripts/stage_role_checks.py` с проверкой CREATE SCHEMA, CREATEROLE, версии сервера, соотношения session/current user и ожидаемого SET для новой роли.
- Если прав создания нет — отказ до DDL. Если ожидаемого SET нет — `STAGE_SET_ROLE_APPROVAL_REQUIRED`, также **до создания схем/роли**. Автоматического GRANT или изменения серверных настроек нет.
- Перед RLS-smoke и учебной проверкой исполнитель делает SET ROLE и проверяет фактическую роль: строго `academy_stage_runtime`, без SUPERUSER/BYPASSRLS/CREATEROLE/CREATEDB/LOGIN/INHERIT, `row_security=on`. При отклонении — ошибка и откат, без проверки RLS административной ролью.
- В успешном результате появляется `rls_test_roles` с признаками реальной ограниченной роли для обоих этапов.
- `--inspect` теперь дополнительно возвращает `creation_capabilities`: версию сервера, `creator_auto_set`, `same_session_and_current_role`, `session_superuser`, `new_role_set_expected`. Это только чтение, без идентификаторов аккаунтов/реквизитов.
- Одобренные файлы `00_preflight_readonly.sql`, `01_schema.sql`, `02_smoke_rollback.sql` и их контрольные суммы не менялись.

## Минимальное предложение, требующее отдельного разрешения

Файл: [creator_set_role.proposed.sql](deploy/stage/creator_set_role.proposed.sql).

```sql
GRANT academy_stage_runtime TO CURRENT_USER WITH SET TRUE, INHERIT FALSE;
```

Эта команда предлагается только после создания новой stage-роли, внутри той же транзакции и до тестов. Исполняющая роль должна быть подтверждённым создателем, `CURRENT_USER = SESSION_USER`. Команда даёт этому создателю право временно переключаться на новую ограниченную роль; она не делает runtime администратором и не даёт runtime BYPASSRLS, LOGIN или доступ к другим схемам. Обратный GRANT административной роли в runtime недопустим.

В PostgreSQL могут существовать две записи членства с разными grantor: автоматическая ADMIN OPTION от системной роли и явное SET от создателя. Тест учитывает их суммарное действие; INHERIT остаётся false.

Предложение **не подключено к scripts.run_stage и не выполнено в Supabase**. Оно проверено только на локальном PostgreSQL внутри откатываемой транзакции. Потребуется отдельное подтверждение, потому что пользователь прямо потребовал остановиться при необходимости расширить права. Предыдущее разрешение на создание тестовых объектов сохраняется; повторно согласовывать весь этап не нужно.

## Проверки

Целевой набор: **29 тестов прошли**. Он включает исходный отказ 42501 → UNKNOWN; отказ нового preflight до DDL; минимальное предложение SET; настоящую ограниченную роль в RLS; чужого владельца с 0 XP; серверные 60 XP без удвоения; полный откат; отсутствие секретов в диагностике; запрет записей в inspect.

Полный backend-прогон: **185 passed**, без пропусков; одно прежнее предупреждение Starlette. Git-коммит указан в итоговом ответе. Frontend в этой правке не менялся, новых визуальных проверок не заявляем. Проверки stage ограничены локальным `_test` на loopback, схемы и роли тестов откатываются.

Настоящие 40 XP не переносились. `public`, `auth`, `storage`, настройки Supabase Auth, рабочие схемы и данные не изменялись. Push, публикация и платные услуги не выполнялись.

## Точная безопасная команда сейчас

Для уточнения настройки SET на настоящем сервере — только чтение:

```powershell
Set-Location 'C:\Users\user\OneDrive\Рабочий стол\academy ai'
$stageCa = Read-Host 'Полный путь к CA-сертификату Supabase'
.\.venv\Scripts\python.exe -m scripts.run_stage --inspect --ca-file $stageCa
```

Пароль — отдельно скрыто, URI — с `[YOUR-DATABASE-PASSWORD]`. Смотрите `creation_capabilities.creator_auto_set` и `new_role_set_expected`. Если они false при ограниченном сессионном пользователе, требуется предложенное SET. Если true, дополнительное право может не требоваться, и историческая причина нуждается в дальнейшей проверке; автоматически считать её найденной нельзя.

До согласования дополнительного SET не запускайте proposed SQL или создание схем вручную. Следующее отдельное согласование: «Разрешаю только право SET для создателя на новую academy_stage_runtime с INHERIT FALSE, внутри ограниченной stage-транзакции; остальные ограничения остаются». После этого предложение можно включить в проверенный план и завершить stage через защищённый ввод в PowerShell.
