# Academy AI — план размещения и синхронизации

Подготовлено 5 ноября 2026 года. Этот документ описывает следующий этап. Текущая реализация отправляет локальные попытки в SQLite домашнего FastAPI через доступный адрес приложения.

## Что уже пригодно для переноса

- UUID каждой попытки создаётся на устройстве и сохраняется до первой отправки.
- Очередь IndexedDB переживает перезагрузку. После завершения ответы попытки фиксируются.
- Один POST обрабатывает все ответы в одной транзакции. Повторный запрос возвращает сохранённое подтверждение.
- Сервер вычисляет правильность, баллы и XP. Итоговый XP за урок ограничен лучшим завершённым результатом.
- Попытка содержит версию урока, отпечаток содержимого, время начала и завершения.
- `server_id` связывает загрузку урока с конкретной базой. Это идентификатор набора данных. Для доступа будущему облачному клиенту понадобится отдельная авторизация.
- `/api/widgets/v1/summary` собирает минимальные данные для будущих виджетов.

## Вариант для бесплатного пилота

Сохранить React PWA и FastAPI + SQLModel. Для публичного пилота рассмотреть статический frontend и FastAPI на Render, а PostgreSQL и Auth — на Supabase. По возможности выдавать frontend и API под одним origin через обратный прокси. При раздельных доменах потребуется точная настройка CORS, cookies и CSRF.

Free web service Render использует временную файловую систему. Изменения локальной SQLite могут исчезнуть при перезапуске или redeploy, поэтому для такого размещения данные следует перенести в отдельную постоянную PostgreSQL. Постоянные диски Render относятся к платным возможностям. [Render Free](https://render.com/docs/free), [Render Disks](https://render.com/docs/disks).

Supabase Free подходит для ограниченного пилота. Проект может быть приостановлен после недели низкой активности, а квоты и условия нужно повторно проверить перед регистрацией. Для личных данных понадобятся собственные регулярные резервные копии и проверка восстановления. [Supabase Pricing](https://supabase.com/pricing), [Supabase Project Pausing](https://supabase.com/kb/faqs/platform/free-project-pausing).

Этот вариант допускает паузы и холодные старты. Постоянная доступность и гарантированная доставка напоминаний потребуют отдельного выбора тарифа или собственного сервера. Подключение сервисов, создание учётных записей и публикация выполняются после разрешения владельца.

## Порядок реализации

1. Проверить бюджет, регион хранения, квоты и способы экспорта. Утвердить домен и конкретных провайдеров.
2. Создать отдельный тестовый контур с обезличенной копией. Реальные ответы и аудио переносить после проверки контроля доступа.
3. Добавить владельца `user_id` ко всем личным данным и однозначное сопоставление старого локального профиля с аккаунтом. Контент уроков оставить общим.
4. Подключить Auth. На backend проверять подпись токена, issuer, audience, срок и владельца записи. Для PWA предпочтительна серверная сессия с `HttpOnly`, `Secure`, `SameSite` cookies и защитой CSRF. Долговременные секреты хранить на сервере.
5. Закрыть все личные API, включая статистику, offline receipts, работы IELTS, настройки и виджеты. Добавить тесты доступа между двумя аккаунтами и отзыва сессии.
6. Адаптировать SQLite-специфичные транзакции `BEGIN IMMEDIATE` к PostgreSQL. Для `(user_id, attempt_id)` использовать уникальное ограничение и транзакционную обработку конкурирующих вставок. Проверить миграции, индексы и часовые пояса на PostgreSQL.
7. Перенести данные с сохранением идентификаторов, связей и истории. Сравнить количество записей и значения всех старых полей. Проверить возврат к резервной копии.
8. Добавить поток изменений с монотонным серверным курсором. Клиент хранит последний подтверждённый курсор, получает страницы изменений и атомарно обновляет свою локальную проекцию.
9. Разделить IndexedDB по аккаунту и окружению. При выходе показывать число неотправленных попыток и предлагать завершить отправку либо экспортировать их. Переключение аккаунта должно блокировать отправку чужой очереди.
10. Проверить сценарии двух устройств, потерянного ответа, истёкшей сессии, изменения контента, конфликтующих черновиков и повторного восстановления резервной копии.
11. Настроить HTTPS, ограничения размера запросов, rate limiting, журналы без текстов работ и токенов, резервные копии и проверку восстановления.
12. После приёмки провести разрешённую публикацию и ручную проверку Windows, Android и iPhone.

## Правила конфликтов

| Данные | Правило |
|---|---|
| Завершённая попытка | Неизменяемое событие с UUID, повтор возвращает прежний результат |
| Один UUID с разным содержимым | HTTP 409 с сохранением обеих доступных копий для разбора |
| Черновик | Номер ревизии, обновление только при совпадении ожидаемой ревизии |
| Учебный контент | Версия и отпечаток, сервер проверяет ответы по соответствующей версии |
| XP и streak | Серверная проекция из принятых фактов |
| Перенос задания | Явная операция с идентификатором и ожидаемой ревизией |
| Удаление | Отдельное подтверждённое событие с tombstone для других устройств |

Сейчас при обновлении урока старая попытка остаётся локально с сообщением о конфликте. Для будущего облака лучше сохранять неизменяемые серверные версии уроков, чтобы принимать работу по старой версии. Это потребует расширения модели контента.

## Время и статистика

Сейчас клиентское время сохраняется в `OfflineReceipt`, а дата активности и streak рассчитываются по времени приёма на сервере. Такой выбор исключает изменение streak произвольными часами устройства. Следующий этап может учитывать доверенный интервал офлайн-сессии, но правило должно быть одинаковым на всех устройствах и отдельно протестированным.

## Напоминания

Текущие напоминания проверяются при открытой видимой странице. Для закрытого приложения нужен серверный планировщик, подписки Web Push, VAPID-ключи, управление отпиской и защита endpoint подписки. Нужно учитывать системную экономию энергии и задержки доставки. На iPhone Web Push связан с установленным на домашний экран web app и пользовательским действием для запроса разрешения. [WebKit о Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

## Контракт будущих виджетов

`GET /api/widgets/v1/summary` возвращает `schema_version`, `generated_at`, `timezone`, `today`, `refresh_after_seconds`, `streak`, `today_tasks`, `subjects`, `masters_countdown`.

| Виджет | Поля |
|---|---|
| Daily Streak | `streak.current`, `streak.longest` |
| Today's Tasks | `today_tasks` с идентификатором, статусом и плановыми минутами |
| English Progress | Элемент `subjects` с `subject=english` |
| Python Progress | Элемент `subjects` с `subject=python` |
| Master's Countdown | `target_date`, `days_remaining`, `past_target` |

Пока точная дата поступления не выбрана в настройках, `target_date` и `days_remaining` равны `null`, ориентир равен 2028 году. Охват тем выражается числами завершённых и освоенных уроков. Данные выдаются с `Cache-Control: no-store`.

Будущие WidgetKit, Android App Widgets и Windows Widgets смогут использовать этот контракт через авторизованный API и локальный снимок. У каждого снимка должен быть возраст данных, срок актуальности и безопасный переход в приложение. Обновление по расписанию зависит от ограничений ОС. Нативный токен следует хранить в защищённом хранилище платформы.
