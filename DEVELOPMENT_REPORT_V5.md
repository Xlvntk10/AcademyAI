## Что изменено

- Корневой `render.yaml` описывает требуемые два сервиса: Static Site для React и Free Web Service для FastAPI. Новый `deploy/Dockerfile.api` содержит только backend, работает от непривилегированного пользователя и не запускает миграции автоматически. PostgreSQL/Auth находятся отдельно в Supabase.
- `deploy/render-static.yaml` согласован с основным конфигом; прежний вариант с одним origin сохранён в `deploy/render-single-origin.yaml` и корневом Dockerfile как отдельная альтернатива.
- Добавлены настройки PWA, SPA Rewrite и запрет кеширования API на CDN. `/api/*` должен проксироваться раньше общего правила React. Адрес API в конфиге пока явно обозначен `REPLACE-API-HOST`: реальный адрес неизвестен до создания сервиса.
- Backend добавляет `CDN-Cache-Control: no-store`, `Surrogate-Control: no-store` и Vary для Cookie/Origin/аккаунта. Персональные ответы не должны попадать в общий кеш.
- Supabase URL проверяется как HTTPS-origin без встроенных реквизитов и путей. Некорректный успешный ответ провайдера, HTML вместо JSON или неполный набор токенов возвращает понятную ошибку 503 без раскрытия содержимого ответа.
- Frontend распознаёт HTML-страницу пробуждающегося хостинга вместо API JSON. Пользователь получает сообщение о повторной попытке; существующие механизмы черновиков и очереди сохранены.
- Добавлена команда `scripts.verify_deployment`: проверяет будущий HTTPS Static Site, четыре маршрута, ресурсы PWA, схему API, режим аккаунтов, запрет анонимного доступа, приватное кеширование и отклонение чужого Origin. Она не отправляет email и не записывает учебный прогресс.
- `CLOUD_DEPLOYMENT.md` переписан как инструкция первого запуска: Supabase Auth/SMTP, отдельные роли PostgreSQL, перенос владельцев, Render/GitHub, backup/restore, откат и обязательные проверки на устройствах. README обновлён.

## Исправленные риски

Исходная основная конфигурация использовала один сервис FastAPI с frontend внутри образа. Для запрошенной раздельной архитектуры необходим проверяемый proxy-контракт: Cookie/Set-Cookie, POST/body, Origin, If-Match и X-Academy-Account должны доходить без искажений. Ослаблять SameSite или переносить токены в localStorage нельзя.

Обнаруженная проблема обработки ошибок: ответ с HTTP 200 от провайдера или хостинга мог оказаться HTML либо некорректным объектом. Теперь такие ответы не воспринимаются как успешный вход/API-результат. Добавлены регрессионные тесты.

## Дополнительная HTTPS-репетиция

Запущены два отдельных локальных HTTPS-процесса: Static Site proxy и настоящий FastAPI в production-конфигурации. TLS проверялся доверенным тестовым сертификатом, PostgreSQL использовала `sslmode=verify-full`. Supabase Auth заменён тестовым HTTP-провайдером с сохранением сессий вне процесса API: это **не проверка реальной отправки OTP**.

1. Миграция `cloud_0001` применена к отдельной PostgreSQL и повторена без ошибки. Runtime использовал ограниченную роль.
2. Копия настоящей SQLite перенесена с проверкой всех строк. Начальный подтверждённый прогресс — 50 XP.
3. Клиент A вошёл, прошёл урок, получил 60 XP. Независимый клиент B того же аккаунта получил этот результат.
4. API остановлен; отправка B получила 503. После повторного запуска API попытка принята, повтор того же UUID вернул прежнее подтверждение.
5. Клиент A получил итоговые 60 XP и streak 1 — повторного начисления нет.
6. Другой аккаунт получил 0 XP и 404 для чужой попытки. Изменение пропорции плана до 70% видно B; устаревшая запись отвергнута с 409.
7. HTTPS-проверка четырёх React-маршрутов и precache прошла. Проверялась HTTP-выдача ресурсов, а не визуальная отрисовка в браузере.
8. Исходная SQLite повторно сверена; все собственные тестовые серверы остановлены.

Первый запуск репетиции выявил ограничение тестового провайдера: его токены жили только в памяти API. Провайдер теста исправлен на отдельное сохраняемое состояние; успешная репетиция повторена на новой тестовой базе. Это не скрытая ошибка production-обновления сессий.

Артефакты остаются локально в `.test-artifacts/v5/`: `result.json`, frontend/build logs, временные сценарии и базы. Они исключены из Git; файлы с тестовыми реквизитами не следует публиковать. Для повторения основных тестов используйте README и отдельную PostgreSQL с окончанием имени `_test`; без PostgreSQL-переменных соответствующие тесты будут пропущены.

## Что требует ручной настройки

1. Разрешение владельца на публикацию/push и перенос реальных данных.
2. Supabase Free project, Project URL, publishable key, session pooler, отдельные административные и runtime-реквизиты.
3. Проверенные UUID пользователей и сопоставление старых SQLite-профилей. Импорт выполняется до первого входа в облачное приложение; существующий профиль не перезаписывается.
4. Настройки шаблонов числового Email OTP и доставки почты. Встроенный SMTP ограничен; для пользователей вне команды нужен собственный SMTP или поддерживаемый почтовый механизм.
5. Настоящие HTTPS-адреса Static Site/API, замена placeholder Rewrite, точный ACADEMY_PUBLIC_ORIGIN и секреты только на backend.
6. Проверка настоящего Render CDN/proxy с двумя независимыми аккаунтами до допуска реальных пользователей. Локальная имитация не доказывает работу внешнего CDN.
7. Docker/Linux-сборка, установка и офлайн-запуск с иконки на физических устройствах, обновление PWA и реальная доставка/обновление сессий Supabase.

## Стоимость и первый запуск

0 ₸ возможны в пределах Free для небольшого личного пилота. Render Free засыпает после 15 минут без запросов, пробуждение может занять около минуты; постоянного диска нет. Supabase Free имеет квоты базы/трафика и может приостанавливаться после недели бездействия. Встроенная почта — только для тестирования, обычно 2 письма в час разрешённым адресам. Бесплатность отдельного SMTP/домена не гарантируется. Источники и подробные ограничения приведены в `CLOUD_DEPLOYMENT.md`.

Безопасный порядок первого реального запуска: разрешение → настройка Supabase/почты/ролей → backup и пробный импорт → согласованный push существующего репозитория → ручное создание двух бесплатных Render-сервисов → проверка HTTPS/API/cookie/no-store → проверка Windows/iPhone → разрешение на перенос рабочих данных. Сначала используйте тестовые профили; не переводите реальные данные на непроверенный origin.

Точные команды миграции, безопасный ввод реквизитов, настройки Render, проверка после публикации, резервное копирование и откат находятся в `CLOUD_DEPLOYMENT.md`. Локальный запуск сохранён в README. Текущая production-сборка рассчитана на Supabase; для локального preview пересоберите frontend с `$env:VITE_ACCOUNT_MODE = 'local'`.
