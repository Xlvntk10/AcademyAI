## Подготовленный исполнитель

Команда `scripts.run_stage`:

1. До ввода реквизитов проверяет контрольные суммы трёх просмотренных SQL-файлов. При изменении плана останавливается.
2. Принимает видимый URI только с `[YOUR-DATABASE-PASSWORD]`, пароль запрашивает отдельно скрыто. Подключается только к Supabase Session pooler на 5432.
3. Использует `verify-full`, проверенный CA, TLS не ниже 1.2; проверяет фактическое использование TLS. Сохраняет исправление Windows-путей сертификата с кавычками/кириллицей.
4. Создаёт объекты одобренного плана внутри одной внешней транзакции. Выполняет прежний smoke-тест внутри savepoint и откатывает его.
5. В отдельном savepoint загружает только авторский начальный каталог из временной SQLite и два вымышленных владельца. Рабочие SQLite не открываются для импорта.
6. Вызывает существующие серверные функции получения урока, проверки ответов, принятия офлайн-попытки и расчёта статистики. Все ORM-таблицы и `search_path` только на этом соединении направлены в `academy_stage`; приложение глобально не перенастраивается.
7. Проверяет 60 тестовых XP, повторную отправку с теми же 60 XP, конфликт изменённого ответа (409), 0 XP у другого владельца и недоступность ему чужого прохождения.
8. Откатывает тестовые результаты, каталог и обоих владельцев. Проверяет пустоту таблиц и неизменность перечня объектов остальных пользовательских схем. Служебные PostgreSQL/TOAST-объекты не принимаются за изменение схем пользователя.
9. Только после успешных проверок фиксирует создание пустых stage-схем и подтверждает версию новой транзакцией. При ошибке до commit откатывается и DDL. При потере связи во время commit сообщает неопределённость и запрещает слепой повтор.

Это проверка настоящих функций бизнес-логики с независимыми ORM-сессиями, **не HTTP-тест двух устройств, не настоящий вход в Auth и не проверка телефона**. Данные авторизации Supabase при этом не читаются и не меняются.

При успешном запуске в Supabase останутся:

- Три stage-схемы, 26 таблиц, 10 последовательностей, 17 явных индексов, 42 внешних ключа и 21 политика RLS.
- Роль `academy_stage_runtime NOLOGIN` с ранее одобренными правами только на stage.
- Одна запись `cloud_0001` в `academy_stage_migrations.alembic_version`.
- Учебные и служебные аккаунтные таблицы пустые. Счётчики последовательностей могут продвинуться: PostgreSQL не откатывает `nextval`. Это не сохранённые XP или личные данные.

## Команда для обычного PowerShell в VS Code

```powershell
Set-Location 'C:\Users\user\OneDrive\Рабочий стол\academy ai'
$stageCa = Read-Host 'Полный путь к CA-сертификату Supabase'
.\.venv\Scripts\python.exe -m scripts.run_stage --ca-file $stageCa
```

Вставьте Session pooler URI с буквальным `[YOUR-DATABASE-PASSWORD]`. Настоящий пароль вводите следующим запросом, скрыто, без URL-кодирования. Не вставляйте URI с настоящим паролем в видимый запрос. Не используйте запись терминала или команды вывода окружения с реквизитами.

Результат без реквизитов появится в `.test-artifacts/supabase-stage-result.json` и терминале. Каталог исключён из Git. Для подтверждения достаточны поля `status`, `supabase_confirmed`, `test_rows_after_rollback` и безопасный код ошибки; пароль и строку подключения отправлять нельзя.

Ожидаемый успех: `status: passed`, `supabase_confirmed: true`, `test_rows_after_rollback: 0`. Если `STAGE_ALREADY_EXISTS` — остановиться и изучить метаданные, ничего не удалять. Если `commit_unconfirmed_do_not_retry_blindly` — сначала проверка состояния без записи, затем решение; повторный запуск не служит проверкой отката.
