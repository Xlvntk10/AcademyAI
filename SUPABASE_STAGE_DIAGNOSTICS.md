# V6.1: диагностика failed_no_commit_requested / UNKNOWN

## Подтверждённые факты

Сохранённый `.test-artifacts/supabase-stage-result.json` содержит `failed_no_commit_requested`, `supabase_confirmed: false`, `UNKNOWN`. Этап выполнения и SQLSTATE в старом формате отсутствуют. Этот файл не перезаписывался при диагностике.

В прежнем коде найден конкретный дефект: `run_stage` передавал внешнее исключение SQLAlchemy в классификатор `check_postgres.diagnose`, который проверяет `sqlstate` только у переданного объекта. SQLAlchemy хранит исходную ошибку psycopg в `.orig`; например, ошибка PostgreSQL `42501` могла превратиться в `UNKNOWN`. Кроме того, не сохранялся этап ошибки и не различались SQL, права, типы Python и миграционные ограничения.

**Это объясняет потерю причины, но не доказывает, что именно 42501 был причиной пользовательской попытки.** Старый отчёт уже не содержит исходных сведений; восстановить их задним числом невозможно. Успешный `SELECT 1` доказывает подключение на момент проверки, но не права на CREATE SCHEMA/ROLE, SET ROLE или выполнение миграции.

## Исправления

- `scripts/stage_diagnostics.py` извлекает ошибки из `.orig`, `__cause__`, `__context__` и сохраняет только проверенный SQLSTATE, стандартное название PostgreSQL-ошибки, безопасную категорию и заранее заданное описание.
- Различаются недостаток прав, создание/переключение роли, необходимость ADMIN OPTION/владения объектом, синтаксис SQL, отсутствующие/существующие объекты, внешние/уникальные ключи, таймауты, блокировки, запрет записи, TLS и сеть.
- `scripts.run_stage` сообщает этап: ввод/конфигурация, соединение psycopg, TLS, инициализация SQLAlchemy, preflight, DDL, RLS, SET ROLE, учебная проверка, откат/проверка объектов, COMMIT/подтверждение.
- Для нераспознанной ошибки Python выводятся семейство исключения и известный файл проекта с номером строки. Текст ошибки, SQL, параметры, локальные переменные и пути с реквизитами не выводятся. Такой случай явно остаётся неклассифицированным, без выдуманной причины.
- Новый `--inspect` работает независимо от файла миграции, не вызывает её и не запускает учебные проверки. Драйвер переводится в read-only **до инициализации SQLAlchemy**. На сервере проверяется `transaction_read_only=on`; все транзакции завершаются откатом.
- `scripts/stage_state.py` читает только системные каталоги, наличие трёх фиксированных stage-схем/роли, агрегированные количества объектов, признаки FORCE RLS и права подключённой роли. Содержимое уроков, сессий, Supabase Auth/Storage и личных таблиц не читается.
- Новый отчёт записывается отдельно: `.test-artifacts/supabase-stage-inspection.json`. Прежний результат остаётся доказательством исходного отказа.

Пароль, URI, адрес сервера и имя подключённого пользователя в отчёты не попадают. TLS verify-full сохранён. Тексты исходных исключений не используются как сообщения пользователю.

## Могли ли остаться объекты

`failed_no_commit_requested` означает, что старый исполнитель не дошёл до явного COMMIT. Его DDL и тесты выполнялись в общей транзакции; штатное завершение с ошибкой должно откатить CREATE SCHEMA, CREATE ROLE и строки. Локальный тест этого поведения прошёл.

Но старый статус **не равен проверке отсутствия объектов**. Они могли существовать ранее или быть созданы другим запуском. При сетевой ошибке также нельзя по одному локальному сообщению устанавливать фактическое состояние сервера. Поэтому текущий статус настоящей Supabase stage пока **не подтверждён**. Реквизиты не доступны агенту, read-only отчёт ещё не получен. Реальные миграции и другие операции записи в Supabase в этой сессии не выполнялись.

## Следующее безопасное действие

Запускать только с `--inspect`:

```powershell
Set-Location 'C:\Users\user\OneDrive\Рабочий стол\academy ai'
$stageCa = Read-Host 'Полный путь к CA-сертификату Supabase'
.\.venv\Scripts\python.exe -m scripts.run_stage --inspect --ca-file $stageCa
```

Вставьте URI Session pooler с `[YOUR-DATABASE-PASSWORD]`; настоящий пароль вводите отдельно скрыто. Ни пароль, ни URI не отправляйте в чат.

Результаты:

- `status: inspection_passed`, `state: absent` — на момент чтения отсутствуют все три целевые схемы и тестовая роль. Это не означает, что миграция разрешена к повтору до изучения причины.
- `state: objects_present_review_required` — есть хотя бы один stage-объект. Отчёт покажет наличие каждой схемы, количества таблиц/последовательностей/индексов, FORCE RLS и тестовой роли. Ничего не удалять и не применять поверх.
- `inspection_failed_no_writes` — проверка состояния не завершена. Смотрите `diagnostic.phase`, `diagnostic.code`, `diagnostic.sqlstate`, `postgres_condition` и безопасные `locations`. Это не доказательство отсутствия схем.

`inspection_confirmed: true` подтверждает только чтение метаданных. `supabase_confirmed` не становится true, потому что новый режим не проверяет успешность миграции и учебного облачного сценария. Содержимое таблиц не анализируется: `data_rows: not_inspected`.

После результата можно установить фактическое состояние и сузить причину. Если чтение успешно, но причина прежнего DDL-сбоя по правам не устанавливается, потребуется отдельно согласованная диагностическая репетиция; автоматически повторять запись нельзя.

## Проверки

- 26 целевых тестов диагностики, исполнителя и SQL-плана прошли на локальной PostgreSQL, включая роль без superuser.
- Проверен именно путь CLI с psycopg `creator`, как в Supabase-команде; TLS verify-full сохранён. Локальный PostgreSQL отклоняет даже DELETE без изменяемых строк в read-only транзакции с SQLSTATE 25006.
- Проверены запрет вызова миграции из inspect, сохранение прежнего отчёта, отсутствие секретов в выводе, раскрытие вложенного SQLSTATE.
- Полный backend-прогон: **182 passed**, без пропусков; одно прежнее предупреждение Starlette/TestClient.
- SHA-256 трёх рабочих SQLite/реестра совпадает с проверенными резервными копиями. Настоящие 40 XP не менялись.
- Frontend и дизайн в этом исправлении не изменялись; новая ручная проверка телефона не заявляется.
