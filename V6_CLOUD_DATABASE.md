Первый файл только читает метаданные. Второй создаёт следующие новые объекты:

| Объект | Состав |
|---|---|
| `academy_stage` | 21 учебная таблица, перечислены ниже |
| `academy_stage_auth` | `users`, `meta`, `sessions`, `auth_limits` |
| `academy_stage_migrations` | `alembic_version`, значение `cloud_0001` |

Отзывает права PUBLIC и возможные автоматические права `anon`, `authenticated`, `service_role` **только на новые тестовые объекты**. Создателем/владельцем остаётся административная роль, выполняющая SQL.

Системные `auth`, `storage`, `public`, рабочие `academy*` и существующие роли не перестраиваются. Пароли, ключи, реальные записи пользователя и Supabase Auth-пользователи в SQL отсутствуют. В новой служебной таблице будет только версия миграции; учебные и аккаунтные таблицы остаются пустыми после smoke-проверки.

Если любое тестовое имя уже занято, сценарий завершится ошибкой до создания объектов. Повторный запуск не перезаписывает существующую схему. Это намеренная защита, а не автоматическое обновление stage.

Третий файл временно использует UUID `00000000-0000-4000-8000-000000000001` и `00000000-0000-4000-8000-000000000002` в собственной таблице `academy_stage_auth.users`. Он не регистрирует почту и не меняет `auth.users`. Все его строки откатываются.

## 3. Граница безопасности и ограничения stage

Backend получает проверенный UUID через Supabase `/auth/v1/user`. Поле владельца из произвольного клиентского тела не становится источником истины. Клиент получает непрозрачную HttpOnly-cookie, а серверные токены остаются в закрытой служебной схеме.

На каждую PostgreSQL-транзакцию сервер задаёт `app.user_id`; RLS отбирает строки этого владельца. Нельзя выдавать runtime-реквизиты браузеру: обладатель этих реквизитов может менять SQL-контекст владельца. RLS здесь дополняет доверенную серверную авторизацию, а не заменяет её. `academy_auth` обслуживает общие серверные сессии и не доступна клиенту через Data API. Администратор миграций остаётся доверенной привилегированной стороной.

**Stage — репетиция структуры и прав, не второй запущенный FastAPI.** Приложение сейчас явно использует `academy`, `academy_auth`, `academy_migrations`. Простое изменение `search_path` не переключит его на stage. Роль `academy_stage_runtime` не может подключаться самостоятельно; проверки используют `SET LOCAL ROLE` из административной сессии. Разрешение LOGIN, пароль и подключение отдельного API не входят в текущий SQL-план. Полный API и синхронизация уже проверены на отдельной локальной PostgreSQL с обычными именами схем.

Не добавлять ни рабочие, ни тестовые схемы в Supabase Exposed schemas. Используем PostgreSQL через FastAPI, а Supabase Auth — как проверенный механизм входа. [Документация Supabase о custom schemas](https://supabase.com/docs/guides/api/using-custom-schemas).

## 4. Безопасный просмотр и повторная локальная проверка

Команды ниже ничего не выполняют в Supabase:

```powershell
Set-Location 'C:\Users\user\OneDrive\Рабочий стол\academy ai'
.\.venv\Scripts\python.exe -m scripts.stage_plan --check
Get-Content '.\deploy\stage\00_preflight_readonly.sql' -Encoding utf8
Get-Content '.\deploy\stage\01_schema.sql' -Encoding utf8
Get-Content '.\deploy\stage\02_smoke_rollback.sql' -Encoding utf8
```

Перегенерация после осознанного изменения Alembic: `python -m scripts.stage_plan`. Команда создаёт только два локальных SQL-файла и не подключается к базам. `--check` сравнивает их с текущей миграцией без записи. Генератор использует настоящую ревизию `cloud_0001`, а не `create_all()` или отдельную вручную написанную схему.

Для тестов выделяется **только локальная** база с именем, заканчивающимся на `_test`, и отдельной runtime-ролью. В этой сессии использована существующая PostgreSQL 17.11 на `127.0.0.1:55456`, с TLS verify-full. Сервер после проверки остановлен. Личные SQLite в него не импортировались.

Если такая база уже подготовлена и запущена, значения вводятся в локальном PowerShell скрыто. Не подставлять URI Supabase вместо локальной тестовой базы:

```powershell
$testAdminSecret = Read-Host 'URI администратора ЛОКАЛЬНОЙ базы *_test с verify-full' -AsSecureString
$testRuntimeSecret = Read-Host 'URI ограниченной роли той же ЛОКАЛЬНОЙ базы *_test с verify-full' -AsSecureString
$env:ACADEMY_TEST_ADMIN_URL = [System.Net.NetworkCredential]::new('', $testAdminSecret).Password
$env:ACADEMY_TEST_DATABASE_URL = [System.Net.NetworkCredential]::new('', $testRuntimeSecret).Password
$env:ACADEMY_TEST_PG_BIN = Read-Host 'Папка локальных pg_dump.exe и pg_restore.exe (без кавычек)'
$env:ACADEMY_ENV = 'development'
$env:ACADEMY_AUTH_MODE = 'local'
try {
    .\.venv\Scripts\python.exe -m pytest -ra
    if ($LASTEXITCODE -ne 0) { throw 'Backend tests failed' }
} finally {
    Remove-Item Env:ACADEMY_TEST_ADMIN_URL, Env:ACADEMY_TEST_DATABASE_URL, Env:ACADEMY_TEST_PG_BIN -ErrorAction SilentlyContinue
    Remove-Variable testAdminSecret, testRuntimeSecret -ErrorAction SilentlyContinue
}
npm.cmd --prefix frontend test
npm.cmd --prefix frontend run build
```

Тесты stage дополнительно запрещают нелокальный host, даже если имя базы заканчивается на `_test`. Полный набор PostgreSQL предполагает заранее созданную рабочую тестовую схему/права из `deploy/grant_runtime.sql`. Тест восстановления создаёт отдельную локальную базу с вымышленными данными и оставляет её для проверки; это не рабочие данные. Без PostgreSQL-переменных соответствующие проверки пропускаются — такой запуск нельзя считать полной проверкой V6.

Для повторной проверки **настоящего** Session pooler без записи используйте существующую команду:

```powershell
$probeCa = Read-Host 'Полный путь к CA-сертификату Supabase'
.\.venv\Scripts\python.exe -m scripts.check_postgres --ca-file $probeCa
```

URI виден только с `[YOUR-DATABASE-PASSWORD]`, настоящий пароль вводится отдельно скрыто. Выбирайте порт 5432 и доверенный CA. Команда выполняет только `SELECT 1`, не запускает миграции. Не передавайте URI/пароль в чат, аргументы команд, отчёты или Git. Для прочих инструментов пароль хранится только в памяти процесса/переменной окружения; не запускайте `Get-ChildItem Env:` и транскрипцию терминала с реквизитами.

Для последующей работы через Session pooler логин отдельной роли имеет вид `ROLE.PROJECT_REF`. Адрес и регион нужно брать именно из своего Supabase Connect. `verify-full` проверяет цепочку CA и имя сервера; отсутствие правильного CA нужно исправлять, не заменять `require`. [Подключения Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres), [проверка TLS](https://supabase.com/docs/guides/platform/ssl-enforcement).

## 6. Откат

- Ошибка создания stage: одна SQL-транзакция откатывает роль, схемы и таблицы. В psql использовать `ON_ERROR_STOP=1`; при открытой ошибочной транзакции выполнить `ROLLBACK` и остановиться.
- Smoke-проверка всегда заканчивается `ROLLBACK`. Даже успешная проверка не оставляет вымышленных результатов.
- Если stage уже создана успешно: оставить её изолированной, не подключать к приложению, не выдавать LOGIN. Удаление схем/ролей потребует отдельного решения; команды удаления здесь намеренно отсутствуют.
- Ошибка будущего импорта: импортёр откатывает всю транзакцию. Исходная SQLite и её копия сохраняются; повторную попытку начинать после изучения причины.
- Ошибка реального размещения: остановить запись в новой версии, сохранить облачный дамп и очереди, вернуть предыдущую версию/config. Не открывать две независимые базы для одновременной записи.
- Для восстановления PostgreSQL использовать `scripts.cloud_backup backup`, затем `restore` **в отдельную пустую базу**, восстановить runtime-grants и сравнить строки. Скрипт запрещает восстановление поверх существующих Academy-схем. `pg_dump/pg_restore` уже проверены на локальных вымышленных данных.
- Этот дамп охватывает только схемы Academy. Он не является резервной копией Supabase Auth, Storage или всего проекта; не менять Supabase-проект/UUID без отдельного плана.

4. После согласованной публикации выполнить `scripts.verify_deployment --url https://<static-site>`; вручную проверить Magic Link, передачу cookie/POST через настоящий Render rewrite, 40 XP, второй браузер, очередь/повтор, выход, холодный офлайн-запуск и настоящее устройство.
